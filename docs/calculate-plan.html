Hard limits from the engine

  • A tensor lives on exactly one device. Experts of a layer cannot be spread over devices.
  • At most 16 phones per host. Traffic between two phones goes through the laptop (a star).
  • What crosses the link per token: one activation of n_embd × 4 bytes. For an 8B model that is 16 KB. The measured adb split is slow because of relay latency, not bandwidth.
  • Changing the placement means a full reload.
Three gaps found in today's llama-server arguments s (verify on the phone first, task T070): in a split the 1.3 GB vision projector would land on the phone; for tied-embedding models like Qwen3-0.6B the output head lands on the last phone unbudgeted; and --fit is on by default and may change the plan we calculated. Fixes: --no-mmproj-offload, a wider -ot pin, --fit off.

3 · Calculate: compute and time for one request

memory fit     weights + context × KV/token + compute buffer  ≤  room on the device
decode / token  t_d = bytes read per token ÷ memory bandwidth     (CPU is memory-bound)
link / phone    h   = α (fixed cost per token) + 2 × 16 KB ÷ link rate
token time      T   = Σ t_d + Σ h + 2 ms          →  tok/s = 1000 ÷ T
first word      TTFT = prompt FLOPs ÷ compute speed (per device) + link cost per batch
whole answer    total = TTFT + (N − 1) × T
MoE             bytes read = dense + experts × active ÷ total   (e, unverified)
vision          TTFT += encoder time, calibrated from the measured 142 s / 2,154 tokens

Inputs and where they come from: unit bytes from the model file (exact) · room per device from live telemetry minus the safety margin m · bandwidth and compute speed backed out of real single-device runs e · link cost α from a 30-second probe, then refined by every real split request e · compute buffers read from the engine's own load log after the first run m. Every value the screen shows carries {value, low, high, source, n}. An unknown shows no number, only a Measure button.

The lesson the screen must teach: splitting is for memory, never for speed. Even over a fast link the phone's compute is below the laptop's, so the best a split can do on this model is tie.

If the laptop only had 4 GB free: it keeps 1.16 GB of fixed tables plus 21 blocks; the phone would need 15 blocks = 2.14 GB, more than its 2.0 → cannot run at 4k, short by 0.14 GB. capable only with a 2k context: phone takes 22–35 (1.89 GB) → ≈1.0 tok/s on the cable, ≈3.2 tok/s on tethering e. Today's planner ignores compute buffers and would wrongly say "fits".

Prior art checked: exo, prima.cpp, distributed-llama, cake and Petals all split automatically, and none shows a predicted time per request before running. That display is MeshAI's differentiator.

What partners see and never see

A partner phone gets a MeshView message over the control plane: devices, the chosen model, the stacks, the verdict and the prediction. By schema it has no prompt, answer or address fields, and a test proves it cannot start or stop anything. The Plan message stays the only thing that makes a phone act.

Keep / remove from today's panel

  • Keep: the RIGHT NOW bar and per-device checklist, one-click USB pairing and the QR, device and model cards, the stacked layer bar, chat with attachments, Stop.
  • Remove or move: the JavaScript fit guess (file × 1.15 + 0.2 GB) → the server's verdict · separate Run and Chat pages → step 3 · "who runs it" and permission lists → a details drawer · the Advanced toggle → one developer drawer.
